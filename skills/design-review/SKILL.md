# Design Review Tool

A human-in-the-loop process for applying visual/layout redesigns to a page. Instead of building a redesign blind, or narrating it in chat, build an interactive review page showing the real current state against proposed variants, then apply only what the user approved. Sibling tool to `article-copy-edit`: same underlying loop, adapted for visual review instead of text.

## Why this exists

Artifacts can't send live clicks back into the conversation; there's no channel from a button in the rendered page back to Claude. So the loop is: build a review page, the user picks a decision per item (optionally with a comment), clicks "Copy My Decisions", pastes the plain-text summary back into chat, and Claude applies exactly what was approved to the real file.

What's different from a copy-edit review is *what's being reviewed*. A layout bug or a proposed redesign needs to be seen rendered, not described in prose, so "before" is a real screenshot of the live page, and "after" is one or more coded mockups built from the page's own real styling, not text.

## When to use

The user wants to change a page's visual design or layout (not its copy) and wants to review real rendered options before anything is built into the actual view. Signals: they ask for a redesign, describe a layout bug, or ask for something like this tool by name.

## The process

### 1. Identify the exact target page/section

Confirm the live route, and which specific section(s) are in scope. A whole-page redesign may still be broken into multiple numbered items, one per section, rather than one giant item.

**Read the design profile if the project has one.** It is a short project file, `docs/design-profile.md` by default, or the path in `PROOFS_DESIGN_PROFILE` (set in the `env` block of the project's `.claude/settings.json`: Read that file rather than echoing the variable). It holds the references the owner loves and dislikes and why, a few rules, the audience and where the tokens live (format: `../../reference/design-profile.md`). Design toward it, and the critic scores `fit` against it (step 4). **It is optional. Never require it.** When it is missing, say so in one line in chat and in the page's `intro_html`, offer to create one with the two questions pages that file describes (references and audience first, then the rules), and go on without it this round: take the tokens from the style guide, or from the site's CSS when there is none, and use the rubric alone. Do not stop to wait for the profile, and never write one the reader did not answer for.

### 2. Capture "before": always from the running app

The "before" is a screenshot of the page as the running app serves it today, never an image committed in the repo (it shows an older page).

**House rules.** Same as every proofs capture skill; full text in `../../reference/house-rules.md`.

0. **Results first.** Nothing matters more than a result the user wants. Save tokens by cutting waste, never by cutting a check, an option or a revise pass the result needs (full text: `../../reference/house-rules.md`).
1. **Finish in this turn.** Build, smoke-check and screenshot before you reply; the next turn re-reads the whole session and costs more each time. Write big files (HTML, spec JSON, scripts) with the Write tool and never print them back with `cat`, `head` or `Read`; the helpers print short summaries.
2. **Stay in two folders.** Read only inside the project (the folder Claude Code started in) and the plugin folder. Do not read parent folders: their `CLAUDE.md` is already loaded for you. Write specs, scratch scripts, screenshots and pages only under `.proofs/` in the project, never the system temp folder, `$TMPDIR` or `~`. The exceptions are the Playwright install in `~/.cache/proofs-playwright` and pr-qa's `PROOFS_BASE_DIR` base folder, when it is set. Write the Playwright folder only with its one install line; never `ls` or Read it to see whether Playwright is there (it is outside the project, so the call is refused): the capture and `--smoke` report a missing install themselves, with exit 2 and the line to run.
3. **One command per Bash call.** No pipes, redirects, `;`, `&&`, `cd`, `$(...)` or `VAR=` in front: Claude Code matches its allow rules against the whole command, and any of those makes it ask (or, in `claude -p`, refuse).
4. **Use the helpers' own checks, not ad hoc tools.** Capture prints each shot's size and overflow; never run `file`, `magick`/`identify` or `sips`, and change your own mockups with Edit or Write, never `sed -i`.

Then, in order:

1. **Find the start command** in the project's `CLAUDE.md` or README, then `package.json` scripts, `Procfile`, `bin/dev` or `manage.py runserver`. If none gives one, **ask the user**; do not switch to screenshots on your own. Missing dependencies are installed with the project's own install command, in the forms the README's `--project` allow block covers (for a Django app with no `.venv`: `python3 -m venv .venv`, then `.venv/bin/pip install -r requirements.txt`, then `--start ".venv/bin/python manage.py runserver 3311 --noreload"`). Do not probe first with `python3 -c "import ..."`: list the setup and run it.
2. **Print "Commands this review will run"** before the first Bash call: one short list with the exact forms (the install, for example `npm install`, or the two Python lines above; the capture line below; the style build if the project compiles styles, or the shot shows the old look; the build and the type check from step 5 if the project has them, in the forms the project uses: `npm run build`, and `npx tsc --noEmit`, or for Vue `npx vue-tsc --noEmit`, or its own `npm run type-check`; a build alone does not check types). Then run them without further narration. The README's optional project block can pre-approve them.
3. **Write the pages file** with the Write tool at `.proofs/capture/pages.json`: a base URL, then one entry per page (start from the example pages file in the visual-qa skill's scripts folder).
4. **Capture with this command**, the same every time. It starts the server, waits for the URL, runs the capture with `PROOFS_BASE_URL` set, then stops the server. One permission prompt is expected.

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/shared/capture/with_server.py --start "npm run dev -- --port 3311" --url http://localhost:3311/ -- node ${CLAUDE_PLUGIN_ROOT}/skills/visual-qa/scripts/capture.cjs .proofs/capture/pages.json --out .proofs/capture/before --sizes 390,1280
```

   - **Read what it found from `summary.md` and `measures.json` with Read**, not with `node -e` or `grep` (Astro run 3: a `node -e` was refused and three greps followed). Each mid-word break is listed with where it is (`midWordAt`: the element, the heading above it, its y in page px and the part shot that shows it); small text, small tap targets and off-center rows carry a `y` too. **A page taller than one part is also saved in parts** (`<name>-<state>-<width>-part-NN.png`, at 1x, at most 4 widths or 1,600 px tall, y ranges in `parts`): open the part a finding names, never the 390 full shot of a long page, which an image reader shrinks until nothing is legible (Astro run 3: 31,000 px tall, and the break was put in the wrong section).
   - It renders a true 390 px phone viewport and writes `summary.md` with measured sideways overflow. **When `summary.md` shows sideways overflow at 390, state it as a finding with the numbers** (for example: the page is 455 px wide on a 390 px screen; the nav is cut off), and show the shot. Hedge only about what was not measured. Open the PNGs and confirm each shows the route you meant.
   - The capture scrolls each page to the bottom and back before the shots, so sections that fade in on scroll are there. **If a row reads `blank or hidden content`, the shot does not show the page below its first screen:** say so in chat and on the page and name what was not seen: that page is not clean. Rerun once; if it is still blank, review only what the shot shows and say why (Astro run 1: every shot was blank below the hero).
   - Use port 3311. The port flag belongs to the dev server: `--port` for Vite (SvelteKit, Vue, Astro), Nuxt and Angular, `-p` or `--port` for Next.js; copy the project's own start command when its README or `CLAUDE.md` gives one, and read `package.json`'s `dev` script otherwise (`vite dev` means `--port`). If the helper prints `server: already answering at <url>; not started by this helper`, the shot may be of another app: rerun on a different port.
   - **Astro 7:** `astro dev` moves itself to the background when an AI agent runs it, so the helper sees it exit before answering; keep it in the foreground with `--ignore-lock` (`--start "npm run dev -- --port 3311 --ignore-lock"`). If a run already left one in the background, stop it with `npx astro dev stop` (or `npx astro dev stop --root <folder>` for another folder).
   - Use `--cwd DIR` when the server starts from another folder. Exit codes: 3 the server never answered (read `.proofs/server.log`), 4 it exited early, 5 another run holds the lock; any other nonzero is the capture's own, and 6 means a page answered HTTP 400 or above or rendered an error page ("Not Found"): that shot is not the page, so fix the pages file's `path` (or the server) and capture again before you build anything on it.
   - **Never start the server yourself with `run_in_background` or `&`.** In `claude -p` the turn then never ends. The helper owns the server and leaves nothing running.
   - **Fallback only on failure, and say which was used.** Playwright missing: run the one-line install the capture prints, once, then rerun. Install declined or failing: take desktop shots with Chrome (`--window-size=1280,900` is fine, with `--disable-features=MacAppCodeSignClone`, which stops a Mac copying its 1.4 GB app per launch) and mark the phone view "not measured" on the page. **Never use Chrome `--window-size` below 500 for a phone shot:** macOS headless Chrome lays the page out at 500 px at narrower sizes. The Chrome browser extension tools are a last resort; if every call fails with "not connected", stop retrying.

**Match the live wording.** Local test data drifts from the live site; bring the real live text into the local copy before capturing, or the "before" pane won't match the picture in the user's head.

**When the app cannot start, stop and ask.** A setup or install command was refused, the dependencies are missing, or the helper exits 3 or 4 and you cannot fix it: write nothing yet, and ask the user to choose, before you build any mockup or page. Offer (a) the exact setup command(s) to approve, one per line in the forms above (for a Django app, `python3 -m venv .venv` and `.venv/bin/pip install -r requirements.txt`), after which you capture the live app, or (b) going ahead from the committed screenshots, labeled on the page as not live. End the turn with that question (in chat, or on a `questions` page if the project uses one); in `claude -p` too, since a refused command will not be approved mid-turn. Never build a review on committed screenshots unless the user chose (b).

With (b), take each screenshot's date from `git log -1 --format=%cs -- <file>`, write in that item's Reason "committed screenshot, last changed YYYY-MM-DD, not the live app", and say at the top of the page (`intro_html`) and in chat that the before is not live and why the app could not run.

Screenshot each in-scope section at the width(s) that matter. The builder embeds each as a data URI (step 4), so the page is self-contained.

No standing-audit section here; raise accessibility or readability points inline in an item's Reason.

### 3. Turn the redesign brief into discrete numbered items

Each item is one section or component:

- Give it coded mockups: real HTML/CSS built from the target page's own fonts, colors, and spacing (the same "reuse the target page's own design system" principle as a copy review), not AI-generated images and not a text diff.
- **A redesign request gets three options, one per role**, set as each variant's `role`: **Careful** (`careful`) fixes what was asked and keeps the structure; **Step up** (`step-up`) is a clearly better layout in the site's own language; **Bold** (`bold`) is a different hierarchy or layout: a different lead, order or arrangement of the main blocks, never only new colors or spacing, and never a brand break or new words. Three roles, because a set of three variations on one idea "barely changed anything" and leaves the reader nothing to choose between. **Give one option for a bug-sized fix or a "Found by the capture" item**, with no `role`: a fix has one right answer, and two extra layouts would only cost the reader time. Follow-up rounds may show more (the worked example's four), when the reader asks for them.
- **Options must differ in layout or hierarchy**, from each other and, for Step up and Bold, from the current page. `--smoke` compares them and prints a line such as `item 2 (Hero): Variant A and the current page are near-copies (0.91)`: that is a problem to fix, not a note. How to read it for each case (a Careful that visibly fixes the problem, a one-option fix) is in `../../reference/design-rubric.md`.
- **Take the section's inventory from the capture before you design.** In the before capture's `measures.json`, find the 1280 shot's `measures.sections` entry for the section this item changes (`summary.md` lists the sections by label) and copy that one object into the item as `before_sections`, and copy the page's `measures.fontSizes` into `before_font_sizes`; `--smoke` compares the options with the page's own section and type scale from them (at 1280, where it measures near-copies). Then every option, and the one proposal of a one-option item, carries `inventory`: one row per captured element, `kept`, `moved` or `removed`, each with a reason (format: `../../reference/review-page.md`). An element with no row shows on the page as "removed — no reason given": the reader's "dropped an element I liked" is caught there, not after the build. Remove little, and only with a reason the reader can accept or reject in one read.
- A single-variant item works exactly like a copy-edit item: no gallery needed, just Original vs. the one proposed variant. Its accept button reads "Use Proposed", not "Use Selected": with nothing selectable, "Use Selected" reads as a control the reviewer has failed to find. The builder does this for any item without `variants`.
- Give every item a **Reason** and a **Recommended / Not Recommended** badge, the same convention as a copy review: your own honest judgment, independent of whether you present the item at all.
- **Never change words the user did not pick.** Build each mockup with the page's copy as it is. If a layout only works with shorter copy, say so in that variant's `note_html` and offer the shorter wording as its own item (or a variant whose label says it changes the copy), so the reader picks it or not (Astro run 3: the build dropped "creating websites with" from the hero headline to fit a split layout, and nobody had picked that).

### 4. Build the review page with the shared builder

**Needs the whole plugin.** This skill reads shared files at `../../reference/` and `../../shared/`, relative to its folder. If they are missing, the skill was copied on its own: install the whole plugin (`/plugin install proofs@proofs`) rather than recreating them.

Write the content; the builder writes the page. Read `../../reference/review-page.md` first: it documents the spec and the command, `python3 ${CLAUDE_PLUGIN_ROOT}/shared/review_page/review_page.py .proofs/design-review/spec.json --out .proofs/pages/<review-name>.html`, with `"decisions": "design-review"`. Do not hand-write the page's JavaScript. Follow any design guidance your environment provides for published pages: "utilitarian but polished," not a landing page. Fill `project` with `name`, `session` and `repo`, taking the session name the way the `working-log` skill does (the session's own name, else one named for the work, kept for the life of the page): the page's header shows the proofs mark, this skill's name, the project and the session, so the user can match the page to its session at a glance.

- **Reuse the target page's own design system** for the mockups (the spec's `css`). Read the project's style guide for its colors and fonts, including dark mode if it has one, rather than trusting a list in this skill, and build against its tokens so the mockups render correctly in every theme the site supports. Give mockup panes their own explicit background rather than letting them inherit the review page's. If the project deliberately darkened its grays to pass contrast, don't "fix" a mockup by reaching back to stock framework grays.
- **Fonts and images.** Use the target page's own font the way the page itself gets it, never by downloading it. If the page links a font stylesheet (for example a Google Fonts `<link>` in its base template), copy that same `<link rel="stylesheet" href="...">` into the spec's `head_html`: the reader's browser loads it, as it does for the site. If the font files are in the project (a `woff2` under `static/` or `public/`), list them in `assets` and point `@font-face` at them from `css` with `src: url({{asset:name}}) format('woff2')`. Either way, end every `font-family` in `css` with a **fallback stack** that resembles the font and a generic family (for a geometric sans such as Space Grotesk: `"Space Grotesk", "Avenir Next", "Segoe UI", ui-sans-serif, system-ui, sans-serif`); the builder warns about a stack with no generic family. Never fetch a font or its CSS with `curl`, `wget` or a script: a network fetch asks for approval (and `claude -p` refuses it), and a linked stylesheet needs no fetch from you. A published artifact loads only Google Fonts stylesheets, so with any other font service say in the item's Reason that the mockup shows the fallback. **Never paste a font's base64 into the spec**: one 22 KB font is about 28,000 tokens, while an asset costs none. Put photos and the before screenshot in `assets` too. The builder embeds every asset **once**, however many mockups use it, and converts PNG and JPEG screenshots to WebP with a PNG or JPEG fallback for older Safari (`image_quality`, `image_max_width`; see the builder reference). Style a screenshot `<img>` by class, not with a `>` child selector: the builder wraps it in a `<picture>`.
- **One item per section**, each with the before screenshot in `body_html`, then either one proposal in `body_html` (the builder then labels the accept button "Use Proposed") or the role `variants` from step 3. Every item gets `reason_html` and `recommended`. **Wrap a one-option proposal's mockup in `<div class="rp-mockup">…</div>`** inside `body_html`: that is how `--smoke` tells the proposal from the before screenshot and its labels, and a proposal without it gets no contrast, tap-target or near-copy check at all. Its `inventory` and `scores` go on the item itself.
- **Crops come from the capture's parts, not from CSS.** For a section of a tall page, put the part shot that holds it (`before/<name>-default-390-part-03.png`) in `assets` and show that, using the section's y from `measures.json` to pick the part; never embed a long page's full shot (Astro run 3: a 31,000 px shot made the page 8.2 MB) and never build a page to measure positions (a "ruler" page, offsets guessed as `margin-top` percentages: Astro run 3 spent about a quarter of the review's turns on it). If no part holds the section whole, show the two parts around it.
- **Put what the capture found on the page, not only in chat.** Any row in the before capture's table that is not about the sections you were asked to change (`off-center rows`, `off-center columns`, `mid-word breaks`, `sideways scroll`, `sections without headings`, and the like) goes in a second `review` section titled **"Found by the capture"**, after the requested items: one item per flaw, its measured numbers and the shot in `body_html`, the fix you would make as the proposal, `"category": "capture"`. These items need no mockup: the capture's own numbers, where the flaw is (`midWordAt`'s element and heading, or the entry's `y`), the part shot that shows it, and one sentence of fix are the whole item. The reader accepts (you fix it with the picks) or denies (you leave it); an offer in chat alone is never seen by someone who reads only the page (Astro run 2: both baseline flaws were caught and offered only in chat). With none, leave the section out.
- **Open decisions go first. Always.** Things needing a decision this round are the first section, above any recap, carried-forward context, or settled material (`after_html`, or a collapsed block). A reviewer should never scroll past what they have already read to reach the first open item.
- **"Mark as read" drops an item from the next round.** The page exports it as `READ`; next round, do not render that item again, not even dimmed. Carrying context forward applies to an *open* item's own history (`history_html`), not to items the reader has finished with.
- **The export's first line is the page's bracketed title**, because pasted decisions arrive in chat with no other context. The builder writes it, plus the variant letter:

  ```
  [Articles Index — Design Review]
  1. Article card layout — ACCEPT (Use Selected: Variant B)
  2. Read More button placement — ACCEPT WITH COMMENT — COMMENT: keep the button but make it teal, not amber
  3. Header spacing fix — REVISE — COMMENT: still too much white space, try tightening further
  4. Footer redesign — DENY
  5. Sidebar links — ACCEPT (Use Proposed) — READ
  ```

Deliver the page as "Where the page goes" below says (with `artifact`, that means publishing it with the `Artifact` tool). Redeploy to the same file path across revisions of the *same* review page; don't mint a new URL for revisions the user is already looking at.

**Verify before publishing, every time and not just the first.** The build runs its own check (script syntax, card and button counts). Run `--smoke`. If it reports Playwright missing, run the one-line install it prints (it uses your installed Google Chrome and downloads no browser), then run `--smoke` again; if it still cannot run, say on the page and in chat that the self-check did not run. `--smoke` already measures sideways scroll at 1280 and 390, and runs the same mid-word measure pr-qa's capture uses on every mockup: a problem such as `item 2 (Feature cards), Variant B: "authenticat|ion" breaks mid-word at 1280px wide` is a problem with that variant. Fix the mockup (a wider box, smaller type, fewer columns) and rebuild; if you keep a variant that breaks a word, say so in that variant's `note_html` and in its item's Reason, and do not recommend it. **Size each mockup to its box before you build it.** At a 1280 px window a variant's box is about 500 px wide when two variants sit side by side and about 320 px with three, and `--smoke` prints every box's width as `mockup_widths`. A mockup of a desktop layout (a 3-column grid, a hero with text beside a picture) does not fit that box: give its item `"stack_variants": true`, which puts one variant per row at about 1,050 px. Never override the builder's own classes (`.rp-gallery`, `.rp-panes`, `.rp-variant`) in `css`.

**Read `--smoke`'s `notes` as well as its `problems`.** A `problems` line is a failure (text below WCAG AA contrast, a tap target under 44 by 44 px at 390, lines over 80 characters at 1280, left edges 1 to 6 px out of line, a mid-word break, sideways scroll, a near-copy): fix that option or drop it, whatever its scores. A `notes` line is what `--smoke` could not judge: "contrast not measured" for text over an image or gradient, and type sizes off the page's own scale. Say every note in that item's Reason and in chat, so nobody reads "not measured" as clean. Then check each "not measured" text by eye on the shot, against the lightest and darkest part of the image behind it; letters crossing a part close to their own color are a contrast failure. An off-scale size is fine when it is deliberate: say why in the option's `note_html`.

**The critic judges every option before the reader sees it.** The reader asked for designs worth choosing between, and a designer grading its own work by memory passes everything. After the build, `--smoke` and the look (next paragraph, which takes the review page's shots at 1280 and 390), score against `../../reference/design-rubric.md`, the current page first:

- **Who scores.** When the session can start a **separate helper with a fresh context** (a subagent, in an interactive session), it judges: give it exactly the inputs the rubric's "Who judges" section lists (the rubric file, the request, the current page's shots at 1280 and 390, each option's shots at both widths, `before_sections`, each option's `inventory`, the style guide's path or the site's tokens, the profile when there is one, and the `--smoke` output), never your reasoning or the options' notes, so it scores what it sees. Tell it to read files with Read, run no commands, and send back the scores with one line for each score of 3 or below. Otherwise (`claude -p`, or no way to start one) score them yourself against the same file, criterion by criterion as a fresh checklist, looking at each shot before its note.
- **What you record.** The current page's scores go in the item's `before_scores` (the page shows them as a "Current page" row); each option's go in its `scores`, and a one-option item's on the item. Set `judged_by` (`helper` or `self`) on **every** item that has a mockup, so the page says who judged; with it set, an option without scores shows "Not scored" and recommending one is a build error. A "Found by the capture" item with no mockup carries neither.
- **The bar.** An option with any criterion at 2 or below, any failed design check, or no gain over the current page on the criterion the request targets is below the bar: revise it once or drop it, with the reason on the page (the rubric gives the wording). Recommend the highest total that clears the bar. Never recommend an unscored option or one below the bar.

Results first: within the $5 est. per-run cap, quality wins. Save tokens by cutting waste (printing big files back, scratch pages built to measure positions, extra rounds), never by cutting an option, the critic or the revise pass.

**One build, then at most one correction pass.** Build, run `--smoke`, then take one look: run `node ${CLAUDE_PLUGIN_ROOT}/skills/visual-qa/scripts/capture.cjs .proofs/capture/review.json --out .proofs/capture/review --sizes 390,1280` with a pages file whose `base` is the `file://` URL of `.proofs/pages/` (an absolute path) and whose entry `path` is `/<review-name>.html` (capture.cjs joins the two with exactly one slash), and open the full-page PNG (its `-part-NN.png` shots, when the review page is tall) to check your coded mockups don't overlap. `--smoke` has already measured 390 for sideways scroll and broken words; the 390 shots are for the critic, who scores every option at both widths. Then run the critic. Fix everything the look, `--smoke` and the critic show in one pass (an option below the bar is revised once or dropped), rebuild, rerun `--smoke`, score each revised option again the same way (the helper gets its new shots), and stop there; capture again only if that pass changed an item's layout, and then open only that item's shot. A problem still left after the correction pass goes in that variant's `note_html`, not into another round (SvelteKit run 1: five rounds of rebuild, `--smoke` and capture, fighting a 500 px box, cost twice what Rails did). Never use Chrome `--window-size` for the phone view. Only publish after all of it passes.

### 5. Applying the decisions

When the user pastes back the copied summary, match items by number (and variant letter, where relevant). **Change only what was picked.** Anything else you think should change (shorter copy so a layout fits, a neighbor section, a word you would put better) is proposed, not applied: leave it as it is and list it in chat as a proposal for the next round, with the item it came from.

- **`ACCEPT`**: translate the selected variant's markup into the real view or template. This is *not* a paste-in the way a copy edit is: the mockup used static stand-in content (a hardcoded example title and image) previewing what a loop over live records will render, so applying it means adapting the chosen structure and styling into the real template, wiring in loops, real image URLs and real data, not copying the mockup's HTML verbatim.
- **`ACCEPT WITH COMMENT`**: same translation, but the comment modifies the result first. Work out what the final design should be from the comment, then build that into the real view. **A comment that says to keep an element** ("keep the testimonial") puts it back into the chosen layout as you apply it, in the place the option's inventory would have given it, because the reader picked the layout and the element both. If it cannot fit without changing the layout they picked, build nothing for that item: say so in chat, with why, and ask whether to drop the element or take another option, rather than starting a new round.
- **`DENY`**: leave the file untouched. A comment here is a note or reason, not an instruction to act on.
- **`REVISE`**: leave the file untouched for now; the comment is feedback for a follow-up round (see below), not an instruction to apply anything yet.
- **`PENDING`**: not reviewed yet; leave untouched.

Then rebuild styles if the project compiles them and verify against a real render. **Do not commit unless the user asked you to** (or the project's `CLAUDE.md` says to commit applied picks): leave the change in the working tree and say in chat that it is uncommitted and which files it touched (Astro run 2: the picks were committed unasked, so the QA session had nothing to commit, and the commit carried a type error). **Build and type-check the change before you say the picks are built.** Run the build if the project has one (`npm run build`, `npx ng build`: whichever `package.json`'s scripts or `CLAUDE.md` name), **and also its type check** when it has a `tsconfig.json` and the change touches `.ts`, `.d.ts`, `.astro`, `.vue` or `.svelte` files: its own `npm run type-check`, `npm run typecheck` or `npm run check` script if `package.json` has one, else `npx astro check` (only when `@astrojs/check` is in `package.json`; without it, it stops to ask to install), `npx vue-tsc --noEmit` (Vue), `npx svelte-check` (Svelte), or `npx tsc --noEmit`. **A build alone does not prove the types:** Vite and Astro builds strip types without checking them (Astro run 2: a broken `.d.ts` passed `npm run build`, and only pr-qa's `npx tsc --noEmit` caught it); `npx ng build` does check them. Fix what either reports; if one still fails, or the project has no such command, say so in chat, naming which ran. **When you are asked to commit, push or open a pull request**, follow `../../reference/commit-and-pr.md`: stage the files you changed by name (never `git add -A` or `git add .`), write a PR body that says what changed, why (the picks) and how it was checked, and when a push fails, report it with the exact command instead of stalling. **When you commit, commit only what you meant to change:** a lockfile (`package-lock.json` and the like) that an `npm install` rewrote is left out of the commit (`git restore` it; `npm ci` installs without rewriting it), and you say in chat that you left it out; if the change does need it, mention it in the commit message or PR. **Verify at every width the layout changes at, not just 1280 and 390:** capture the real page at `--sizes 390,1280,1440` plus one width just above each breakpoint the applied markup uses (as pr-qa picks them: Tailwind `sm:` 656, `md:` 784, `lg:` 1040, `xl:` 1280, `2xl:` 1552; Bootstrap `md` 784, `lg` 1008, `xl` 1216, or the project's own). **Compare that after capture with the before**: add `--compare .proofs/capture/before/measures.json` to the capture line, and read its "new since the earlier capture" list in `summary.md`, which matches entries by text, not by count, at every width both captures took. Any entry it lists that is in the area you changed (a small tap target, small text, a mid-word break, an off-center row, an element wider than the screen) is a failure this change caused, even when the total went down (Astro run 3: small tap targets went from 11 to 9 and 3 of the 9 were new footer links, 37 to 43 px wide): fix it and capture again with `--compare` before you say the picks are built, and say in chat which entries were new and how they were fixed. Widths the before did not take are listed as "no earlier capture"; check those rows against the targets. Any `mid-word breaks`, `sideways scroll`, `off-center rows`, `off-center columns`, `blank or hidden content` or new `text below floor` row in the capture's table is a failure **if this change caused it**: fix it and capture again before you say the picks are built (Rails run 1: cards built at 1280 and 390 looked right, and broke "authenticat / ion" at 992 and 1440). If the before capture shows the same row, it was already there: list it in chat as already there and leave it, unless the reader accepted it under "Found by the capture". A `sections without headings` row is a note, not a failure. The review tool changes nothing about how the actual change gets verified and shipped.

### 6. Follow-up rounds on `REVISE` items

Scope the new Artifact to only the still-open item(s). Carry the prior round's rejected proposal forward on each card in `history_html` (clearly labeled "Round 1," "Round 2," etc.) alongside the new one, rebuild and republish to the same URL, re-running the verification before every republish; a smaller page is not a lower-risk page. Items the reader marked read are dropped, not carried.

## Worked example

A review of a tab row on a mobile measurement screen: the row overflowed on a phone with no wrap or active state, and the list below never filtered by type. Two rounds:

- **Round 1**: one proposed variant per concern (layout, active state, filtered list) plus a first pass at a new "see all" modal. The reviewer accepted the tab-row item outright; the modal trigger was sent back ("too much whitespace next to the button") with a request for several genuinely different options, since there was no preference to start from.
- **Round 2**: scoped to just the still-open modal trigger, with four real alternatives (grid tile, icon-only button, plain text link, list-header link) instead of one refined guess. The list-header link was accepted.

What made this work, worth repeating:

- **Test the review page's own buttons by measuring, not by eye.** Round 1 shipped a mobile/desktop width toggle that looked fine but did nothing: the two-up gallery capped each preview's rendered width below the breakpoint it needed to cross. It was caught by measuring the element's bounding box before and after the click in a headless browser. Round 2 replaced the toggle with fixed-width mobile and desktop frames side by side (in their own `overflow-x: auto` container, so the page body never scrolls sideways), leaving no interaction to silently fail.
- **"I don't have a good option, show me a few" is itself a valid Round 2 request.** The reviewer doesn't have to know what they want. REVISE with a vague comment is exactly what a follow-up round is for, and four distinct answers served better than refining one guess in place.
- **Show the rejected first-round idea dimmed.** Round 1's proposal stayed on the same card as Round 2's new options, visually de-emphasized (dimmed, dashed border): enough context to see what changed without competing with the live decision.
